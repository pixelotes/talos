# 0003. Rust as the implementation language

- Status: Accepted
- Date: 2026-11-24
- Review: after v0.1, with real data on iteration cost (see Consequences)

## Context

The primary constraint is low resource use on small ARM hardware. The existing
Python implementation rests at roughly 250 MB resident, most of it interpreter
and scientific libraries, and takes hundreds of milliseconds per turn end to
end. Deployment needs a virtual environment and compiled wheels for the target.

The workload is small and CPU-bound: string matching, a sparse dot product,
SQLite queries, template filling. There is no need for a large ecosystem.

The codebase will be written largely with AI assistance, so a compiler that
rejects whole classes of mistakes is worth more than usual.

## Decision

Implement Talos in Rust, on the stable toolchain, as a Cargo workspace.

- The engine crate is synchronous and free of async and network dependencies.
- Optional weight sits behind Cargo features (`server`, `net`).
- Dependencies must be permissively licensed and justified individually.
- Python is allowed only as a development-time tool (classifier training, pack
  building), never at run time.

## Consequences

- A single static binary per target; cross-compilation to ARM64 and ARMv7 is
  routine. No interpreter, no virtual environment on the device.
- Memory at rest in the low megabytes is realistic, with no garbage collector
  pauses.
- Turn context as an owned value passed through typed stages is enforced by
  the compiler, which removes the "handler lost the language" class of bug.
- Slower iteration than Python and a steeper learning curve. Compile times
  must be watched; the dependency policy helps.
- The decision is revisited once, when v0.1 closes: if iteration cost has been
  a brake, switching to Go is still cheap at that point and is reconsidered
  before the classifier and the knowledge store are built.
- Skills written by third parties in other languages need the external skill
  protocol ([0013](0013-external-skills.md)).

## Alternatives considered

- **Go.** Simpler, fast builds, easy cross-compilation, good standard HTTP.
  Costs a runtime and garbage collector (tens of megabytes at rest), weaker
  sum types for modelling outcomes, and cgo or a transpiled SQLite. A
  reasonable second choice if iteration speed proves to be the bottleneck.
- **Python, slimmed down.** The floor is the interpreter plus the classifier
  library; it cannot reach the budget.
- **Zig or C.** Smallest output, but a thin ecosystem (Zig) or too little
  safety (C) for a project of this size and team.
